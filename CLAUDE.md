## Known Issue Under Investigation

- **Linux gain-wheel input delay with Spectrum Fill:** captures show old wheel events delivered in batches while plotting continues; gain callbacks and subsequent readout paints are fast. Suspected JUCE/X11 dispatch issue: selective paint-completion checks can leave input queued inside Xlib while the socket is no longer readable. The isolated mechanism is reproduced locally; causality inside Open-Q remains unconfirmed and no JUCE fix is applied. The user deferred JUCE patching; check Release behaviour before revisiting a framework change. See [capture protocol and findings](yohan-docs/gain-input-timing-test.md), [X11 probe](yohan-docs/x11-queued-input-probe.cpp), and `source/ui/GainTimingTrace.h`. Ctrl+Shift+T starts/stops capture and exports `Open-Q-gain-timing*.csv` to the system temporary directory. Native queue instrumentation is a possible follow-up if Release testing warrants reopening the investigation. Preserve Fill and existing paint pacing; do not dispatch native events from gain controls or during painting.

## Fixed Regressions to Preserve

- **macOS gain-entry CI focus:** synthetic clicks do not activate AppKit like real clicks. Keyboard-entry tests must use a focusable peer, promote the macOS console test process with `Process::setDockIconVisible(true)` before requesting activation, verify root/editor focus and await asynchronous editor closure instead of sleeping 20 ms. Preserve Return commit, Escape/focus-loss cancellation and exact host-gesture counts; never activate the application from plugin controls to accommodate tests.
- **Cross-platform paint pacing:** meter polling/painting shares the graph's admitted VBlank frames through `onFrameRefresh`; an independent meter animation timer can cause native dirty-region consolidation to repaint the plot outside its budget. Keep the editor timer for gain-drag heartbeat and settings, and drain hidden meter latches without animation. Pacing uses one monotonic clock and reserves actual paint duration after measured completion, even beyond the capped recovery estimate. Test per-frame input windows rather than a short wall-clock paint-share percentage. Keep the periodic meter stimulus separate from continuous synthetic edits: explicit input may force native redraws outside the automatic budget. Use finite wheel bursts with unique logical event timestamps, retaining strict idle-window assertions; see the follow-up in the stall diagnosis document.
- **Analyzer selections overwritten by refresh:** ComboBox changes notify asynchronously. Compare each selector's model field with the last displayed settings before refreshing it; unconditional timer writes can erase a pending user selection before `onChange`. Unrelated Pre/Post changes must not overwrite it either. Regression coverage is in `AnalyzerConfigurationTests.cpp`.
- **Linux CI native-window tests:** run Xvfb with Openbox and wait for both display and window-manager readiness. Bare Xvfb can leave JUCE's `WM_PROTOCOLS` atom unset and abort native-peer tests with `BadAtom`.
- **Exact trim unity:** use continuous trim parameter ranges. JUCE's convenience float constructor adds 0.01 dB snapping whose fused arithmetic can move zero slightly negative. Preserve exact zero through host conversion, automation and state recall; keep bit-exact dry audio coverage in `GainMeterTests.cpp`.
- **UI stalls after adding opaque meters/footer:** requiring the entire graph bounds to be repainted disabled paint-cost feedback when JUCE clipped those edges. Expensive spectrum fills then starved input handling. Measure visible plot redraws, retain an input window after long paints, and keep the 200 ms stalled-gain-drag cancellation guard. Regression coverage is in `ResponseGraphTests.cpp` and `GainMeterTests.cpp`; see [diagnosis and verification](yohan-docs/gain-meter-ui-stall-diagnosis.md). The user confirmed improvement from that fix; the separate known wheel-delivery issue above remains unresolved. Preserve these checks when changing layout, opacity or repaint scheduling.

- **Timing CSV tests:** compare recorded values numerically with the actual parameter value, using a suitable tolerance. Do not require an exact decimal spelling such as `0.500000000`: host normalization can differ slightly under fused arithmetic. Value-initialize all synthetic `MouseWheelDetails` fields; the JUCE struct has no default field initializers. Synthetic wheel events also need explicit unique timestamps; wall-clock time can repeat during timer catch-up.

## About This Project

This project is derived from the [Pamplejuce](https://github.com/sudara/pamplejuce) template — a JUCE audio plugin template using CMake, C++23, and modern CI/CD. Open-Q builds VST3, CLAP and Standalone on Linux, Windows and macOS, with AU/AUv3 additionally enabled on macOS.

The template provides the build system, CI/CD, and project structure. The plugin-specific logic lives in `source/`.

## Build Commands

Initialize dependencies once: `git submodule update --init --recursive`.

```bash
# Debug development build (matches the VS Code tasks)
cmake -S . -B Builds -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCMAKE_EXPORT_COMPILE_COMMANDS=ON -DJUCE_BUILD_EXTRAS=ON
cmake --build Builds --config Debug --target OpenQ_VST3 OpenQ_Standalone AudioPluginHost --parallel 2

# Functional tests (excludes the separately registered boot benchmark)
cmake --build Builds --target Tests --parallel 2
ctest --test-dir Builds --output-on-failure -E "Boot performance"

# All CTest entries, including the boot benchmark
cmake --build Builds --target Tests Benchmarks --parallel 2
ctest --test-dir Builds --verbose --output-on-failure

# Release build for making music / checking CPU usage
cmake -S . -B Builds/Release -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_EXPORT_COMPILE_COMMANDS=ON -DJUCE_BUILD_EXTRAS=OFF
cmake --build Builds/Release --config Release --target OpenQ_VST3 OpenQ_Standalone --parallel 2

# Benchmarks
cmake --build Builds --target Benchmarks --parallel 2
./Builds/Benchmarks
```

Development defaults to **Debug**. Use **Release** for audio performance checks or if Debug causes high CPU or dropouts. VS Code's Run Build Task lists the Debug and Release tasks; F5 launches AudioPluginHost on Linux. Load `Builds/OpenQ_artefacts/Debug/VST3/Open-Q.vst3` in the host, then set plugin breakpoints.

## Architecture

**SharedCode Library**: The `SharedCode` INTERFACE library links plugin source code to both the main plugin target and the Tests target, avoiding ODR violations.

**CMake Modules**:
- `PamplejuceVersion.cmake` - Reads VERSION file, optional auto-bump patch level
- `PamplejuceFunctions.cmake` - One include that defines the `pamplejuce_*` functions below (and turns off their legacy include-time behavior)
- `PamplejuceIPP.cmake` - Intel IPP integration (optional)

Target setup happens via explicit function calls in `CMakeLists.txt`, not at include time:
- `pamplejuce_add_assets()` - Includes all files in assets/ as binary data (from `Assets.cmake`)
- `pamplejuce_add_tests()` - Configures the Catch2 test target (from `Tests.cmake`)
- `pamplejuce_add_benchmarks()` - Configures the Catch2 benchmark target (from `Benchmarks.cmake`)
- `pamplejuce_shared_code_defaults()` - C++23 and compiler defaults (from `SharedCodeDefaults.cmake`); Open-Q removes its fast-math flags to preserve finite-value checks
- `pamplejuce_xcode_prettify()` - Xcode folder/scheme cleanup (from `XcodePrettify.cmake`)

Note: after `include(PamplejuceFunctions)`, a plain `include(Tests)` (or Assets, etc.) is a no-op - call the function instead.

**Test Discovery**: Functional tests use `catch_discover_tests()` with `PRE_TEST` discovery mode for Xcode compatibility. The separate `Benchmarks` target also registers its cases with CTest; build it before running all CTest entries.

## Code Quality

Always resolve any compile warnings encountered during builds. Warnings should be treated as errors and fixed before considering a task complete.

Note: LSP/clangd often reports false positive diagnostic errors (like "undeclared identifier", "file not found") because it doesn't have full context of the JUCE module system. Ignore these unless the actual build fails.

## Includes

JUCE modules include common standard library headers (`<vector>`, `<algorithm>`, `<string>`, `<memory>`, etc.) so you don't need to add those explicitly in JUCE code. Adding them is harmless but redundant.

## Threading Model

- **Audio thread:** runs `processBlock`; never block, allocate or lock.
- **Message thread:** owns components, painting, input and UI timer callbacks.
- **Workers:** the editor owns response/analyzer workers; preserve their existing ownership and shutdown paths.
- Parameter listeners may run on the thread that changes the parameter, including the audio thread. Never assume they are UI callbacks or touch components from them.
- Use parameter atomics for simple values, existing SPSC triple buffers for response frames, and the fixed-capacity analyzer FIFO for audio packets. Each SPSC channel has one producer and one consumer; do not add readers/writers casually.
- Poll audio-to-UI state from message-thread callbacks. Do not trigger `AsyncUpdater` from the audio thread: posting a system message can block. Preserve the existing meter latch and graph-paced refresh paths.

## Realtime Safety

For anything in the audio thread / hot DSP path (e.g. `processBlock`):
- Allocate in constructors or `prepareToPlay`, not while rendering audio
- Avoid dynamic allocations and container growth (`std::vector::push_back`, map insertion, string building)
- Prefer fixed-size storage (`std::array`, preallocated buffers, fixed-capacity queues)
- Keep operations deterministic and lock-free where possible

## Adding Dependencies

Reuse existing helpers and dependencies before adding another library. JUCE modules live in `modules/` as git submodules; add them with `add_subdirectory`/`juce_add_module` as appropriate and link to `SharedCode`. Non-JUCE libraries use the existing CPM setup. Pin new dependencies to a specific version or commit, preserve notices, and record their purpose/license in `THIRD_PARTY_NOTICES.md`.
